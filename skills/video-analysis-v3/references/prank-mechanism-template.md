# 整蛊/道具机制分析标准模板

用于 v3 在“逐秒客观观察”之后、本地合成最终脚本之前执行。这个模板不是总结材料，而是输出标准的一部分。

## 必须新增的本地推理层

在 `observations.json` 之后，先生成 `story_analysis`，再渲染 HTML：

```json
{
  "genre_guess": "整蛊/道具机制/关系博弈",
  "confirmed_facts": [],
  "mechanism_hypotheses": [],
  "verification_windows": [],
  "safe_final_story": "",
  "core_points": [],
  "replaceable_parts": [],
  "must_not_claim_without_verification": []
}
```

## 整蛊故事链

每条整蛊/魔术/关系博弈视频都必须追问：

1. 诱饵是什么？钱、礼物、手机、承诺、节日理由、挑战奖励。
2. 谁是受害者/被套路的人？TA 以为发生了什么？
3. 实际发生了什么？是否有换道具、遮挡、机关、可擦/可变状态？
4. 道具的物理属性是什么？露底、空心、漏出、透明、双层、可擦、隐藏。
5. 结果如何被可视化证明？钱掉出、标记出现、对方无法反悔、道具暴露。
6. 谁最终获利/谁被套住？

## 机制假设候选

生成 2-3 个候选，不允许只停留在“疑似换瓶/疑似变化”：

- 诱饵—误判—道具机关—揭示/获利
- 容器结构机关：露底/空心/漏出/透明/遮挡
- 换瓶/换道具/掉包机制
- 承诺规则机关：用可见证据让对方无法反悔
- 标记/涂抹机关：X、颜色、印记、文字突然出现

每个候选必须包含：

- `name`
- `likelihood`: high / medium / candidate / rejected
- `story_question`: 下一步必须追问的问题
- `evidence_for`
- `evidence_against`

## 关键帧复核规则

Gemini 只做观察，不直接写最终故事。凡出现以下信号，必须加入 `verification_windows`，建议抽取 `t-2s` 到 `t+2s` 密集帧，必要时裁剪手部/道具区域：

- 物体身份改变：纸币 → 纸巾、白瓶 → 黑瓶、手中物 → 地面物
- 人物短暂遮挡核心道具
- 道具从一人手里转移到另一人手里
- 容器底部、盖子、开口、透明区域可能影响结果
- 钱/纸状物消失、露出、掉落、被捡起
- 结尾有人离开后另一个人获利

目标问题必须具体，例如：

- 黑瓶/容器底部是否可见？是否像露底/没底？
- 钱/纸状物放入后是否从底部露出或掉出？
- 女人/受害者拿走的是哪个容器？
- 男人/施术者拿到的钱是否来自瓶底、地面或遮挡区域？
- 两个相似道具是否在同一时刻并存？

## 最终 HTML 标准

最终用户看到的 HTML 必须使用上传案例的样式和结构，而不是把审计过程当主表：

1. 标题卡：`视频总结归纳 + 脚本表`
2. `视频整体内容总结`
3. `核心爆点`
4. `可替换部分`
5. `脚本表`

脚本表固定列：

| 时间 | 画面内容 | 动作 | 关键对白/旁白 |
|---|---|---|---|

要求：

- `画面内容` 只写拍摄准备信息：地点/场景、在场人物、必要道具。越短越好，例如“厨房内；丈夫、妻子；碗、抹布”。
- `动作` 写导演分镜式动作、表情、情绪变化和笑点推进，不粘贴 Gemini 逐秒原文。
- `关键对白/旁白` 有音频就忠实翻译并保留说话人/换行；无明确音频就写“无明确对白/旁白，主要靠画面动作推进”。
- `核心爆点` 和 `可替换部分` 要像案例模板一样以卡片呈现。
- `story_analysis`、机制假设、审计摘要、逐秒观察只能折叠在附录，不能作为主输出。

## 禁止事项

- 未复核容器底部时，不得写“露底/没底”为事实。
- 未看到钱的归属变化时，不得写“某人拿走钱/获得钱”为事实。
- 遮挡处发生的动作只能写“疑似/需要复核”，不能写成确定事实。
- Gemini 的解释性词语（偷偷、欺骗、以为、目的）不能直接进入最终故事，必须经本地证据链验证。
