# Universal Story Mechanism Framework

V3 的通用目标：不是只描述画面，而是从客观观察中推导“这个视频为什么成立”。所有视频都必须走这套三步骤，再按类型加载子模板。

## 总流程

```text
Gemini 客观观察
→ 本地整合人物/动作/道具/音频/字幕
→ Step 1 故事假设生成
→ Step 2 关键机制验证
→ Step 3 人类逻辑层解释
→ 输出安全最终故事 + HTML 脚本表
```

## Step 1：故事假设生成

先判断视频类型，再生成 2-3 个候选机制。不要只输出“疑似发生了什么”，要明确每个候选解释的是哪一种故事逻辑。

### 类型初判维度

从以下信号判断类型，可多标签：

- 人物关系：夫妻/情侣、朋友、路人、商家顾客、老板员工、亲子。
- 内容动力：冲突、诱惑、挑战、承诺、利益、教程、测评、反转、情绪释放。
- 关键载体：对白、道具、身体动作、字幕、第三方人物、产品展示、环境变化。
- 结果形态：打脸、抓包、获利、惩罚、和解、证明有效、失败翻车、转化购买。

### 候选类型库

优先支持这些高频短视频类型：

1. 关系喜剧 / 夫妻关系类
   - 夫妻吵架
   - 夫妻好色
   - 妻管严
2. 整蛊 / 道具机制 / 魔术
3. 挑战 / 打赌 / 承诺兑现
4. 教程 / 技巧 / 步骤演示
5. 带货 / 测评 / 痛点证明
6. 街访 / 路人反应
7. 纯剧情反转 / 误会解除

### 候选机制字段

每个机制假设必须包含：

```json
{
  "type": "关系喜剧/整蛊/教程/带货/...",
  "name": "机制名称",
  "likelihood": "high|medium|candidate|rejected",
  "story_chain": ["起点", "冲突", "升级", "反转/结果"],
  "evidence_for": [],
  "evidence_against": [],
  "verification_questions": []
}
```

## Step 2：关键机制验证

每个类型都要把“故事是否成立”的关键点转成可验证问题和时间窗口。

### 通用验证问题

- 谁是主导者？谁被动？关系强弱是否发生变化？
- 核心冲突/诱饵/承诺是什么？
- 转折点在哪一秒发生？
- 结果有没有可见证据？
- 是否有遮挡、物体身份变化、音频/字幕缺失导致的不确定？
- 结论是否依赖不可见动机？如果依赖，必须降级为“大概率/疑似”。

### 关键帧窗口生成规则

出现以下情况必须加入 `verification_windows`：

- 道具或物体身份改变。
- 人物关系/权力状态突然改变。
- 有人被抓包、被打脸、认怂、获利。
- 字幕或对白推动承诺/威胁/总结。
- 关键动作发生在遮挡或快速移动中。
- 结尾出现结果证据。

每个窗口包含：

```json
{
  "start": "00:07",
  "end": "00:11",
  "reason": "验证丈夫是否从偷看转为搭讪，并确认妻子是否察觉。",
  "questions": ["谁在看谁？", "动作是否被伴侣发现？", "是否有惩罚/翻车信号？"]
}
```

## Step 3：人类逻辑层

最终故事必须解释观众为什么能看懂，而不是只串联动作。

### 必须回答

- 观众期待是什么？
- 哪个行为打破期待？
- 情绪如何变化？平静→自信→尴尬→愤怒→认怂？
- 笑点来自哪里？反差、误会、抓包、嘴硬失败、规则套住、欲望暴露？
- 结尾是谁赢/谁输/谁被打脸？
- 哪些元素可替换复用？

### 安全表达等级

- `confirmed_fact`: 画面/字幕/音频明确支持。
- `likely_interpretation`: 多个证据支持，但含动机或隐含逻辑，用“大概率/像是/可以理解为”。
- `unsupported_claim`: 缺少证据，不进入主输出。

## 输出到 HTML 的方式

主 HTML 只呈现成熟结论：

- 视频整体内容总结：用安全最终故事。
- 核心爆点：用人类逻辑层总结。
- 可替换部分：用类型模板提炼。
- 脚本表：按时间段展示画面、动作、对白/旁白。

过程产物只能折叠或留在 JSON：

- 类型候选
- 机制假设
- 验证窗口
- 反证/不确定点
- blocked claims
